Prioritizing Which Pages to Review First: Historical Freshness and Search-Performance Signals vs. a Transparent Rule Baseline

Can historical content-freshness and search-performance signals help prioritize which pages deserve human review, and does a learned model improve the precision of a transparent rule-based baseline on unseen clients?

Shaik Raihan Basha · FlyRank ML Internship Capstone

Repository · Capstone notebook

Overview

Abstract

This paper uses the anonymized FlyRank ML Internship dataset as a public-safe case study of a practical content-operations problem: content teams often have more pages than they have editorial capacity to review, so they need a defensible way to decide which pages deserve human attention first.

The problem in one paragraph

This project is a public-safe case study of a content-prioritization problem represented by the FlyRank ML Internship dataset. Content teams can accumulate far more pages than they have capacity to inspect, while changes in content freshness and search performance can make it difficult to decide where review effort should go first. Given limited editorial or content-review capacity, which pages should be reviewed first? The prioritization system developed here directs human attention toward pages whose historical freshness and search-performance signals are associated with declining performance. Its output is a ranked review queue: decision support for deciding what to inspect, not an automated system that changes content.

Why a baseline is necessary

A model is only useful if it beats the obvious alternative. The transparent rule baseline is that alternative: a simple, explainable scoring rule based on content staleness, search visibility, click-through rate, and search position. Because both approaches are evaluated on the same client-grouped holdout with the same labels, any difference between them is attributable to the method itself, not to different data or different validation design.

What success means here

Success is measured by whether the model concentrates more labeled-declining pages near the top of the review queue than the rule baseline — in other words, whether it improves Precision@20 and Precision@50 on clients it has never seen. Accuracy, precision, recall, and F1 provide additional context. Because the practical workflow has limited review capacity, the quality of the top of the queue matters more than an unrestricted prediction over every page.

Data

Dataset and release

This project uses the anonymized FlyRank ML Internship starter dataset, data/raw/content_refresh_anonymized.csv, provided as part of the internship workflow. It is a public-safe research dataset: it contains no client names, domains, URLs, page titles, keywords, or raw search queries — only hashed identifiers plus numeric and categorical metrics.

  • Rows: 30,000 anonymized content items (one row per page)
  • Clients: 32 pseudonymized clients
  • Columns: 44 in the shipped export; 45 in the validation workflow after deriving the target label
  • Window: metrics are aggregated over a trailing 90-day window ending at export time (feature semantics documented below)

Because the available materials document trailing-90-day metrics but do not provide a public calendar date range, this paper describes the observed windows using the documented feature semantics rather than inventing start and end dates.

Unit of analysis

Each row is one anonymized content observation associated with a client and its measured content and search-performance attributes. The declining-content target is is_declining_label, derived from the observed trend direction: is_declining_label = (trend_direction == "down"), where down reflects a recent 30-day impression comparison. In this dataset, 16,262 of 30,000 rows (54.2%) carry the declining label — the observed base rate.

Identifiers and how they are used

client_id is used only to build the grouped validation split; content_id is treated as a row identifier. Neither is used as a predictive feature, and no attempt is made to map the hashed identifiers back to any real entity.

Exclusions and why they were made

The following fields are excluded from the predictive feature set:

Excluded fields and the reason for each exclusion
FieldWhy it is excluded
is_declining_labelThe target itself
trend_directionDirectly used to define the target
trend_pctSource information used to derive the trend direction
client_idGrouping identifier; must not become a shortcut for client-specific patterns
content_idRow identifier rather than a generalizable content signal

These exclusions reduce the risk of leaking label information into the model and prevent the model from learning client- or row-identity shortcuts instead of patterns that may generalize to unseen clients. No rows were dropped: all 30,000 rows are partitioned into training (23,837) and test (6,163) sets.

Public-safety constraints

All findings reported here are aggregate, model-level, or metric-level results. No raw dataset values, row-level identifying details, or private queries are reproduced in this paper.

Methodology

Prediction target

The supervised target is is_declining_label, defined from whether the observed trend direction is down. The target is used only for evaluation; it and its source fields are never included as features.

Features (the final model uses six predictors)

The six historical features used by the final Random Forest
FeatureWhat it represents
content_age_daysDays since the content was created (every row in this slice is ≥ 90 days old)
days_since_last_updateDays since the content was last updated
impressions_90dSearch impressions over the trailing 90-day window

Assumptions

The primary assumption is that the available historical features are appropriate for a decision-support ranking setting. The results are interpreted as measured associations and ranking performance on this dataset — not as causal evidence that changing a page improves its performance.

Transparent rule baseline (Week 4)

The baseline is a hand-written, fully explainable scoring rule rather than a learned model. A page receives positive signals when it is stale (a long time since its last update), receives meaningful search impressions, has a low click-through rate, or ranks outside the first page of search results. The conditions are combined into a transparent score (0–3 in the grouped evaluation) that produces human-readable reason codes such as STALE_VISIBLE, LOW_CTR, LOW_VISIBILITY, and HIGH_PRIORITY_REVIEW. This provides a meaningful comparison: the model is judged against a practical rule-based approach, not against nothing.

Random Forest model

A Random Forest classifier is used as the machine-learning approach. It was selected as a practical nonlinear model that can learn interactions between freshness and search-performance signals without requiring the prioritization rule to be specified by hand, and that provides feature-importance output for interpretability. The reported numbers are measured performance for this model configuration on this dataset and validation design; they do not establish that Random Forest is universally the best model for content prioritization.

Evaluation metrics

Both approaches are evaluated as ranked prioritization systems. The primary metrics are Precision@20 and Precision@50 — the proportion of truly declining pages among the top 20 and top 50 ranked recommendations — because a human team may only have capacity to review a limited number of pages. Accuracy, precision, recall, and F1 are reported for additional context. The model and baseline are evaluated on the same test rows and against the same labels.

Validation design: client-grouped holdout

The primary validation uses a client-grouped split (via GroupShuffleSplit, 80/20, fixed seed random_state=42):

  • 25 training clients · 7 test clients · 0 client overlap
  • Training rows: 23,837 · Test rows: 6,163

Why client grouping matters: if pages from the same client appear in both training and test data, the model can memorize client-specific patterns and look better than it actually is. Grouping by client means the test set contains only clients never seen during training, so the evaluation asks a harder and more honest question: does the model generalize to a client it has not seen? A random-row split was run as a diagnostic, and its results are reported alongside the grouped results because the gap between them is itself a finding (see Results).

Leakage checks

A feature-level leakage audit was run on the final feature set. It confirmed that none of the known target-source fields or identifiers (the target itself, trend_direction, trend_pct, client_id, content_id) are model features, and it reviewed the timing of the historical window features. A deliberate leakage diagnostic showed the stakes: when target-derived trend information was introduced as a feature, evaluation performance became artificially perfect (Precision@50 = 1.0) compared with 0.70 for the clean grouped model — clear evidence of leakage rather than model quality. A column-level audit documents the checks but does not prove complete temporal safety for every production scenario; a production deployment would require explicit feature and prediction timestamps and a point-in-time pipeline.

Reading the result honestly: gains and trade-offs

  • Precision@20 improves substantially — from 0.55 to 0.85. In this held-out evaluation, 17 of the top 20 model-ranked recommendations were labeled declining, versus 11 of the top 20 from the baseline.
  • Precision@50 improves — from 0.52 to 0.70, so the improvement holds when the queue is expanded.
  • Accuracy improves — from 0.4897 to 0.5629.
  • F1 improves slightly — from 0.5813 to 0.5928.
  • Recall decreases — from 0.6932 to 0.6227. The model’s prioritization strategy may miss some pages labeled as declining.

This is not an across-the-board improvement. The model appears better suited to prioritizing top-ranked review candidates, while the recall trade-off should be weighed depending on the operational objective: if the goal is to find as many declining pages as possible (broad coverage), the rule baseline caught more of them; if the goal is to make the most of a small review budget, the model concentrates declining pages near the top of the queue.

On this evaluation, the model’s primary value is concentrated at the top of the ranked queue.

What the result means operationally

The results support using the model as a decision-support ranking tool, not as an automated decision-maker. If a review team can inspect roughly 20 pages, the held-out evaluation suggests the Random Forest ranking concentrates more declining pages near the top of the queue than the rule baseline. A recommendation triggers human review — where context can determine whether an observed decline reflects content quality, seasonality, competition, search-result changes, or something else — rather than an automatic content change.

Limitations & Honest Framing

This section states what the work cannot claim. Every item below is supported by the notebooks or is an explicit constraint of the experimental design.

Observational study, not causal evidence

The results are based on patterns observed in the provided anonymized dataset. The model identifies associations between historical signals and the declining-content label; it does not establish that any individual feature causes content performance to decline. A page that has not been updated recently may appear frequently among declining pages, but this does not prove that updating it will improve performance.

Proxy label, not a complete measure of content quality

The target is derived from an observed trend (trend_direction == "down"). A declining trend can have multiple explanations — changes in search competition, seasonality, search-result layout, indexing, user intent, or factors not in the feature set. A positive prediction is a recommendation for review, not proof that the content is poor or requires a refresh.

Dataset scope

The analysis is limited to the 30,000-page anonymized starter slice. It documents trailing-90-day feature windows but does not claim a public calendar date range, and it should not be read as a complete production data specification.

Generalization is evaluated on a limited number of clients

The grouped holdout uses 25 training clients and 7 test clients with zero overlap — a stronger evaluation than random-row splitting, but still a small number of held-out client groups. Performance may differ for clients, content types, industries, traffic levels, or search environments not well represented here.

Dataset-specific performance and temporal drift

The reported metrics are measured on this dataset and validation design; Precision@20 = 0.85 should not be read as a guaranteed improvement in every future environment. Model performance can change as the data distribution, client population, search behavior, or underlying search systems change. The action queue can also become stale: the monitoring plan tracks shifts in the label rate, feature distributions, model-score distribution, and performance on newly labeled held-out data before any retraining decision.

Historical metrics and temporal safety

The feature set includes historical signals such as trailing-90-day impressions. Column-level leakage checks and exclusions were performed, but a column-level audit cannot prove complete temporal safety for every production scenario. A production implementation would require explicit feature timestamps, prediction timestamps, and a point-in-time pipeline so every feature available to the model existed before the prediction decision.

Ranking vs. causal inference

The system ranks pages for review; it does not measure whether reviewing or refreshing recommended pages increases traffic, clicks, rankings, or other downstream outcomes. That would require a separate intervention-tracking design. The evaluation therefore reports predictive and ranking performance, not business impact.

Threshold dependence of the operational queue

The out-of-sample review queue maps model probabilities into priority buckets (HIGH, MEDIUM, LOW — 1,201, 1,870, and 3,092 of 6,163 rows respectively). Those buckets depend on the chosen probability cutoffs, so the distribution of effort across priorities would change with different thresholds.

Recall trade-off

Recall fell from 0.6932 (baseline) to 0.6227 (Random Forest), and 1,188 false negatives were observed in the grouped test set (19.28% of test rows). The model’s prioritization strategy may miss declining pages, so it is best suited to prioritizing a limited review queue rather than to claiming it identifies every declining page.

The model does not replace human judgment

A high-ranked page should be reviewed alongside context the model does not see: seasonality, content strategy, marketing campaigns, search competition, business priorities, and editorial constraints. The recommended workflow is model ranking → human review → decision → action → post-action measurement.

Ranked Recommendations

The action playbook (w07_action_playbook.ipynb) turns the validated model output into a human-review priority list. The queue answers one narrow question: which pages should a reviewer inspect first? The model score determines priority; reason codes tell the reviewer what to investigate. Counts below come from the 6,163-row out-of-sample queue.

  1. 1

    Review multi-signal candidates first

    Highest priority

    Action: Full human review of search intent, content accuracy, freshness, competitive context, technical factors, recent performance, and business value. Multi-signal candidates (522 of 6,163 queue rows) are the highest-priority archetype for comprehensive review.

    Reason: When several observed signals point the same way (reason codes such as AGE, STALE, VISIBILITY, CTR, PERFORMANCE combined), the case for earlier inspection is stronger than any single signal alone.

    Priority / confidence: Priority 1 · HIGH queue bucket.

    Decision purpose: Focus the first review pass on the most defensible candidates. Multiple signals support priority — they do not prove the content caused the observed decline.

  2. 2

    Review freshness and update candidates

    Priority 2

    Action: Review factual accuracy, topic freshness, changes in user needs, and opportunities to update content. Refresh-candidate archetype (90 queue rows).

    Reason: Pages with relatively high content age or a long time since their last update carry AGE / STALE reason codes. Observed directionally, the top-20% model-score band had a lower median content age (181 days) than the rest of the queue (326 days) in this test population — an observed difference, not a causal claim.

    Priority / confidence: Priority 2 · MEDIUM–HIGH queue buckets.

    Decision purpose: Decide which older or rarely-updated pages deserve an update review. Verify the topic changes, facts are current, the page was not just edited, and the performance pattern is persistent before acting.

  3. 3

    Review visibility candidates

    Priority 3

    Action: Review search intent, page structure, internal linking, content coverage, and competitive context. Visibility-candidate archetype (45 queue rows).

    Reason: Weaker observed search position carries the VISIBILITY reason code. A weaker position should trigger investigation rather than an automatic refresh.

    Priority / confidence: Priority 3 · MEDIUM queue bucket.

    Decision purpose: Decide whether a positioning issue is a content, structure, or competition problem. Verify intent, competing results, page structure, and persistence before acting.

  4. 4

    Review CTR candidates

    Priority 4

    Action: Review title and meta presentation, search-intent alignment, and how the page appears relative to competing results. CTR-candidate archetype (275 queue rows).

    Reason: Relatively low click-through rate carries the CTR reason code and is the most frequent single-signal archetype in the queue.

    Priority / confidence: Priority 4 · MEDIUM queue bucket.

    Decision purpose: Decide whether presentation, intent alignment, or SERP layout explains low CTR. Low CTR alone does not prove the content needs rewriting.

  5. 5

    Investigate performance candidates

    Priority 5

    Action: Investigate recent performance and demand context before allocating refresh effort. Performance-candidate archetype (1 queue row in this holdout).

    Reason: Relatively weak recent performance carries the PERFORMANCE reason code.

    Priority / confidence: Priority 5 · MEDIUM–LOW queue buckets.

    Decision purpose: Decide whether weak recent performance is demand-driven (seasonality, changing search interest), temporary, technical, or worth the review effort at all.

  6. 6

    Monitor lower-priority candidates

    Priority 6

    Action: Track future performance and reconsider the page if its ranking or observed signals change materially. The Monitor archetype covers 5,230 of 6,163 queue rows — most of the queue.

    Reason: Lower model-based priority should not immediately consume limited review capacity.

    Priority / confidence: Priority 6 · LOW queue bucket.

    Decision purpose: Protect review capacity so higher-ranked candidates get attention first, while keeping lower-priority pages on a watch list.

Reason codes describe observed characteristics. They are not causal explanations of why a page declined.

Human-review gate and automation boundary

Before approving a content action, a reviewer checks: search intent, accuracy, freshness, competitive context, performance context, technical context, business value, and recent edits. The system should never automatically publish rewritten content, delete content, alter factual claims, change prices or legally important information, modify medical or safety-critical information, make irreversible SEO changes, declare a page permanently “low quality”, or claim that a refresh caused an improvement. The safe boundary is model ranking + explanation → human review → human decision.

Monitoring and when to revisit the model

The queue becomes stale when the declining-label rate, feature distributions, or model-score distributions shift materially, when the content population changes, when the target definition changes, or when grouped-holdout performance degrades on newly labeled data. Those are investigation triggers, not automatic retraining commands; the strongest signal for revisiting the model is degradation on new held-out data evaluated with the same grouped validation logic.

Final recommendation

Based on the measured results, the recommended deployment pattern is to use the Random Forest as a human-review prioritization system: use the model to decide what to inspect first, use reason codes to understand the observed signals, and require human review before making content changes. This keeps the system aligned with the evidence produced by the project while avoiding unsupported causal or fully automated claims.
